### <a name="_qmphm5d6rvi3"></a>**Решение**

Ключевая идея заключается в том, чтобы добавить **промежуточный слой (ACL)** между цифровыми каналами (Сайт, Интернет-банк, Кол-центр) и АБС, чтобы:
- снять нагрузку с АБС и не делать «каждый клик клиента = запрос в АБС»;
- обеспечить быстрый отклик (кэш/справочники/предрасчёты);
- централизовать заявки, статусы, уведомления;
- дать возможность развивать микросервисы вокруг депозитов, не переписывая весь интернет-банк.

**Основные компоненты MVP**
1) **Deposit Application Service (Сервис заявок на депозит)**
- принимает заявки с сайта/интернет-банка;
- хранит жизненный цикл заявки;
- интегрируется с системой кол-центра (создание лида/обновление статуса);
- интегрируется с АБС через адаптер (получение статусов “ставка подтверждена / депозит открыт”);
- инициирует отправку СМС уведомлений (через существующий СМС-шлюз).

Технологии: **.NET** (экспертиза в банке), БД **MS SQL** (уже есть в банке). 

2) **Deposit Rates Service (Сервис ставок/продуктового каталога депозитов)**
- отдаёт список депозитных продуктов и актуальные ставки (общие);
- отдаёт персонализированные ставки для клиента интернет-банка;
- на MVP допускается, что источник ставок — АБС (новые таблицы/модуль ставок) либо управляемый бэк-офисом справочник, но уже не XLS “в почте”.

Решение для MVP: модуль ставок в АБС (Oracle) + API/выгрузка в Rates Service (кэш). Это сохраняет контроль и аудит в “центральной” системе и упрощает переход к целевой автоматизации.

3) **ABS Integration Adapter (адаптер интеграции с АБС)**
- единая точка входа/выхода для интеграций с АБС;
- реализует “бережный” режим к АБС (очередь/пул/лимиты/кэш, где возможно);
- преобразует модель данных АБС в модель каналов

Технологии: **Java**

4) **OTP/SMS компонент в составе канального слоя**
Требование: подтверждение по СМС есть, но “в ядре интернет-банка” и его лучше не дорабатывать у подрядчика.

Решение: реализовать отправку/проверку OTP **в канальном слое** (в Application Service), а интернет-банк вызывает его по API. Это уменьшает зависимость от подрядчика, сохраняя использование текущего СМС-шлюза.

**Логика выбора и ключевые решения**
1) Избавляем цифровые каналы от прямой связи с АБС
Причина: перегрузка БД АБС и риски доступности. 
Решение: канальный слой (DAS/DRS) + адаптер к АБС.

2) Перевод ставок из XLS в управляемый контур

Причина: ставки сейчас “живут” в XLS и передаются почтой; это тормозит процесс и усложняет интеграции. 
Решение MVP: модуль ставок в АБС (Oracle) + выдача ставок наружу через Rates Service (кэш/быстро).

3) OTP/SMS без доработки ядра интернет-банка подрядчика

Причина: функционал СМС “в ядре”, доработка требует подрядчика, чего лучше избегать. 
Решение: вынести OTP в DAS (команда банка), интернет-банк вызывает по API.

4) Производительность

Причина: требуется отклик “в миллисекундах”, есть проблемы со справочниками > 1 секунды. 
Решение: DRS (кэширование справочников/депозитных продуктов), минимизация запросов к АБС, горизонтальное масштабирование сервисов.

5) Технологии

Причина: желательно использовать существующий стек (MS SQL, Oracle, .NET, Java), и совместимость платформ. 
Решение: новые сервисы на .NET + MS SQL; адаптер к АБС возможен на Java.


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

A1. Прямая интеграция интернет-банка с API АБС

Почему отклонено: в задании указано избегать прямой работы ИБ с АБС из-за перегрузки БД и рисков доступности. 

A2. Оставить ставки в XLS и “подтягивать” их в сервис

Почему плохо: XLS — не управляемый источник, проблемы с доступами/аудитом/версией, высокая ручная составляющая. Противоречит цели цифровизации и масштабируемости. 

A3. Kafka для событий/очередей уже в MVP

Ограничение: текущая платформа интернет-банка несовместима с Kafka. 

Вывод: Kafka — оставить на следующий этап.

**Недостатки, ограничения, риски**

1) Дублирование данных и консистентность

Deposit Rates Service (Сервис ставок/продуктового каталога депозитов) будет кэшировать/реплицировать часть данных (продукты/ставки). Нужны правила актуализации и SLA обновлений.

2) Сложность интеграции с АБС

АБС “тяжёлая” (Oracle/PLSQL) и масштабируется вертикально; адаптер должен ограничивать нагрузку, иначе риски сохранятся.

3) Доступность интернет-банка

Команда ИБ считает требования 99,9% сейчас невыполнимыми. MVP потребует пересмотра инфраструктуры (балансировка, горизонтальное масштабирование). 

4) Зависимость от подрядчиков (кол-центр/ИБ)

Интеграции должны быть стабильными контрактами (API), иначе сроки MVP не будут выполнены.

5) Безопасность

Поскольку передаются персональные данные клиентов (ФИО, телефон, параметры вкладов), требуется шифрование трафика, контроль доступов и журналирование критичных операций.
